## 1. 추천 방향으로 정한 것 (바꾸고 싶으면 알려 주세요)

| 결정 | 정한 값 | 이유 |
|---|---|---|
| 읽는 층 | ① 30초 브리핑 → ② 기사 요약층(한 줄 핵심 + 요점 3줄 + 수치) → ③ 자세히(본문) | 위층만 읽어도 핵심이 빠지지 않게. 임원은 ①, 실무자는 ②, 관심 있는 사람만 ③ |
| 요점 3줄의 칸 | **무엇이 · 얼마나 · 어디까지** (라벨 고정) | 설계서 1장의 독자 질문("무엇이 달라졌고, 어디까지 확인됐는가")에 그대로 답한다. 고정 라벨이라 매주 같은 자리에서 같은 정보를 찾는다 |
| 30초 브리핑 줄 | 핵심은 한 줄 핵심, 단신은 제목 | 모델 호출을 늘리지 않고 원고에서 코드가 만든다 |
| 분량 | 핵심 본문 220~300 → 150~220, 단신 60~95 → 45~75, 총론 100~170 → 70~120, 더 볼 거리 70 → 60, 합계 2,000 → 1,600자 | 요약층이 핵심을 맡으므로 본문은 줄인다. 요약층을 넣어도 전체 글 양은 현행과 비슷하거나 적다 |
| 확인 단계 표시 | ●●●○ 네 칸 막대(구상·연구 → 도입 계획 → 현장 실증·적용 → 양산·상시 운영) | 성숙도 꼬리표를 글 대신 한눈에. 그림이 아니라 글자라서 사내 메일 프로그램에서도 똑같이 보인다 |
| 읽는 시간 | 머리띠에 "전체 약 N분", 브리핑에 "약 N초" | 바쁜 독자가 어디까지 읽을지 먼저 정한다 |
| 꼭지 표식 | 이모지·번호 대신 꼭지 색 이름표 | 30초 브리핑의 01~06 번호와 겹치지 않게 |
| 이전 응답 호환 | 모델이 한 줄 핵심·요점을 빠뜨리면 본문 첫 문장으로 대신하고 요점은 생략 | 사내 모델이 새 키를 못 따라와도 발송은 멈추지 않는다(검토 요청 ②에서 보인다) |
| 기본 테마 | **B4** (`config.yaml`의 `internal.newsletter_theme`) | 아래 비교 참고 |

## 2. 비슷한 수준의 두 안 — B4와 B5

| | **B4 요점 카드 (추천·기본)** | **B5 스마트 브리핑** |
|---|---|---|
| 느낌 | 밝은 민트, 카드형. 현행 B3를 다듬은 모습 | 짙은 남색 머리띠, 뉴스레터 앱 같은 미니멀 |
| 핵심 기사 | 제목 → 한 줄 핵심(꼭지 색) → 요점 3줄(라벨 칸) → 수치 카드 → **자세히(본문)** → MTC가 볼 것 | 왼쪽 큰 숫자 열 + 오른쪽 한 줄 핵심 · 요점 · "그래서 MTC는". **본문 없음** |
| 견본 글자 수(화면 글자) | 약 3,100자 | 약 2,700자 |
| 장점 | 본문이 있어 배경·조건이 궁금한 사람도 메일 하나로 끝. 현행 독자에게 낯설지 않다 | 가장 짧고 훑기 쉽다. 숫자가 먼저 눈에 들어온다 |
| 단점 | 스크롤이 B5보다 길다 | 배경·방식을 알려면 원문을 찾아야 한다(사내에서는 링크가 없어 번거롭다). 요점이 비면 내용이 부족해진다 |
| 바꾸는 법 | `newsletter_theme: B4` | `newsletter_theme: B5` |

**추천은 B4**입니다. 링크를 넣을 수 없는 사내 메일이라 "더 알고 싶을 때 갈 곳"이 메일 안에 있어야 하고, 요약층 덕분에 본문을 안 읽는 독자도 B5와 같은 속도로 핵심을 얻습니다.
B5는 독자가 대부분 임원이고 회신·문의로 깊이를 보충하는 운영이라면 더 맞습니다.

## 3. 사내 운영 전에 확인할 것

- 사내 모델이 `deck`·`points`를 실제로 잘 쓰는지 첫 호에서 확인한다(검토 요청 ②의 [D] 아래 ▶·· 줄로 보인다). 요점 문장 수정은 지금은 [E] 수정안 또는 `review/{주차}-draft.yaml` 직접 수정으로 한다. 검토 요청 문법에 요점 수정 칸(예: `D 핵심1.얼마나="…"`)을 넣는 일은 다음 작업으로 남겼다.
- 사내 메일 프로그램(Outlook 등)에서 B4·B5의 둥근 모서리·띠 색이 어떻게 보이는지 한 번 열어 본다. 표 기반·인라인 스타일이라 깨지지는 않지만 모서리는 각지게 보일 수 있다.
